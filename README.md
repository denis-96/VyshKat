# ВышКат: «Доедем до дедлайна»

Консольное приложение учёта парка кикшеринга НИУ ВШЭ. Проект использует .NET 10,
встроенный контейнер `Microsoft.Extensions.DependencyInjection`, xUnit и Moq.

## Запуск

```text
dotnet run --project VyshKat.App
dotnet test
```

При запуске UI добавляет демонстрационные данные, после чего позволяет принять
самокат, велосипед, шлем или зарядную станцию, посмотреть энергопотребление,
транспорт для новичков и весь инвентарь. Самокат с инвентарным номером, содержащим
`BROKEN`, отклоняется реализацией `TechnicalInspectionService`.

## Архитектура и SOLID

- `IInventoryItem` задаёт только инвентарный номер для объектов на балансе.
- `IEnergyConsumer` задаёт только суточное энергопотребление. Поэтому велосипед и
  шлем не обязаны реализовывать не относящийся к ним контракт (ISP).
- `Vehicle` расширяется новыми видами транспорта без изменения отчётов
  `FleetManager`. Энергопотребляющий транспорт дополнительно реализует
  `IEnergyConsumer` (OCP).
- `FleetManager` отвечает за учёт и отчёты, а `TechnicalInspectionService` — за
  решение техосмотра; `BeginnerVehicleRule` — за правило доступности новичкам
  (SRP).
- `FleetManager` не принимает повторяющиеся инвентарные номера. Проверка общая для
  транспорта и вещей и не зависит от регистра букв.
- `FleetManager` принимает `ITechnicalInspectionService` и
  `IBeginnerVehicleRule` через конструктор, а
  `Program` связывает интерфейс с `TechnicalInspectionService` в DI-контейнере
  (DIP). Сервис контейнера зарегистрирован как `Transient`, менеджер парка — как
  `Singleton`, поскольку он хранит состояние приложения.
- Наследники `Vehicle` и `Thing` используются через их базовые типы и контракты,
  не требуя от клиента знания конкретного класса (LSP).

### Осознанное ограничение

`ConsoleUserInterface` одновременно читает ввод, показывает меню и вызывает
сценарии менеджера. Это небольшое нарушение SRP принято для учебного консольного
приложения: выделение отдельных команд и классов добавило бы код без пользы
для текущего требования. Доменная логика при этом остаётся в `Domain` и `Services`.

## Расширение системы

Новый вид транспорта добавляется наследованием от `Vehicle`; отчёты парка уже
работают с базовым типом, поэтому `FleetManager` менять не нужно. Если новому виду
нужна энергия, он реализует `IEnergyConsumer`.

Сотрудник намеренно не принимается `FleetManager`, потому что сотрудники не входят
в баланс. Для них можно добавить отдельную модель и сервис кадров. Склад запчастей
также лучше оформить отдельным `WarehouseManager`, не смешивая его состояние с
активным парком.

## Тестирование и DI

В `FleetManagerTests` зависимости `ITechnicalInspectionService` и
`IBeginnerVehicleRule` подменяются моками. Тесты проверяют отклонение техники,
успешную приёмку и факт вызова техосмотра. Тест
`GetBeginnerFriendlyVehicles_ShouldUseInjectedRule` показывает, что правило можно
заменить без изменения `FleetManager`; параметризованная теория отдельно фиксирует
стандартный порог 6. Тест отчёта проверяет суммирование только объектов,
реализующих `IEnergyConsumer`.

## Использование ИИ

ИИ использовался как помощник для оформления консольного интерфейса, идей тестов и
проверки требований. Типы доменной модели, сервисы, правила технического осмотра и доступности новичкам,
сценарии консольного UI и финальная проверка проекта были разработаны и проверены
вручную.
